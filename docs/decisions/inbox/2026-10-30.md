### 468. [mimic-overlays] A character's overlays are remembered automatically, and the Canvas is theirs (Mimic beta `b906c15f`, 2026-10-30)
The guild lead, after raiders said overlay setup "has become a lot" and "I thought the overlay sets were going to simplify
it": *"save the state for each character as changes are made, make them a 'last overlay' that comes back up when you swap to
that character. Make sure we remember if someone was using the canvas, and don't automatically move other overlays into
canvas unless the user wants it."*
- **Automatic, not opt-in.** One snapshot per character (the overlay-set snapshot: which overlays are on, where, size, look,
  height floors, the Canvas on/off and its panels) in `overlay-last.json` beside `overlay-sets.json`; not a named set, not
  in the 40-set cap or the sets list. Written by itself 2 s after a change settles (never during hide-all, a drag, or the 3 s
  after Mimic applied a layout; flushed at quit and when the character is left). The opt-in visibility-only profile
  (`charProfilesEnabled`) is used for a character only until they have a last layout; the explicit "Save layout" stays as a
  manual snapshot. "Forget" forgets both. `cfg.charLastLayoutOff = true` is a field escape with no control.
- **Multi-box:** the screen belongs to one character. A swap applies the new character's layout only when the character the
  screen belongs to has had no Zeal sample for 60 s (`/api/state` `zealClients[].updatedAt`, numeric ms; the agent drops a
  client after 45 s), or at the first look after launch. Both clients live (alt-tabbing): nothing moves. Unknown client list
  never counts as quiet.
- **A new character inherits the screen as it is**: nothing invented, nothing moved into the Canvas for them.
- **Canvas panels are per character**: `cfg.canvasLayouts` was one shared slot, so a character switching the Canvas on
  inherited another's panels and their overlays left the screen for it. That was the implicit "moved into the Canvas" path.
  The audit found no other path that turns the Canvas on by itself; the explicit ones stay (toggle, tour button, Arrange after
  "yes", Split callouts, a bound group hotkey, an approved layout import).
- Same change set, same day: Target Info re-fits its window after a resize (Mimic beta `ae0b9ed9`); the other nine overlays
  that report a raw height are not audited yet.

### 473. [pop-progression] `/pop/events`: every scripted PoP event, item scores and a ranking; Relv / Falto as an optional Storms step (web 2.1.69, 2026-10-30)
The guild lead: *"add this [the Relv / Falto, Lord of Thunder event] to the pop guide for plane of storms as an optional event. Please
comb through the PoP LUA scripts and get us a repository of those events and include the loot that can drop and the percentages. Give item
scores to each item and then add a ranking that could be there for each event."* Then: *"count procs and focus effects higher, PLUS ATTACK
for melee"*. Calls made in the draft (any is a small change):
1. **Score = a 0 to 100 class-relative index**: for each class that can use the item, the gear finder's raw points (level 65, no worn
   gear) divided by the best item of that class on the page; the item's score is its best class's index, with the top three classes
   named. Reason: raw points follow the class tables (a Rogue's weights are fatter than a Cleric's), not item quality. Items that cannot be
   worn (tokens, patterns, gems) have no score and add nothing to an event's value; they are listed as other loot.
2. **Page-only tuning** (`EVENT_SCORE_TUNING` in `web/lib/popEventsScore.ts`), replacing the finder's flat +2 per focus and +1 per proc:
   focus +35 caster, +20 hybrid, +5 pure melee; proc +30 melee class, +45 on a melee weapon, +5 anyone else; a melee class's attack
   counted twice (the 250 cap kept). Sized against the 120 to 300 raw points a PoP wearable scores (a focus is worth a real stat line).
   The size of the focus or proc is not read. `gearWeights.ts` and `/me/upgrades` are unchanged; the same tuning could go global.
3. **Event value per run** = Σ over the event's loot mobs of kills × (chance ÷ 100 × the table's rolls) × score; also the best item, the
   classes with a drop scoring 50+, and the chance of at least one 80+ item. Kills are 1 unless a script gives a number (the Falto
   mephits 15 + 15, the mepheekas 90); waves of trash in unstated numbers are under-counted. Drop limits are not in the mirror.
4. **Data**: the event list is committed (100 events from SecretsOTheP/quests @ 572bc06, cites linked to the lines); drops, item stats
   and the guild's average DKP per item are read live and cached 6 h. Members only, like `/pop/raid`.
5. **Guide**: step `storms_relv_falto`, optional, no flag (the script sets none), `who: raid`, links to `/pop/events#postorms-relv-falto`.
   Regenerating `apps/mimic/pop-quests.js` and `utils/popEngine.js` is data only: no Mimic or bot version bump.

### 474. [web] Guest Mimic links: an officer-approved, time-limited key that uploads parses only (bot 4.0.35 + web 2.1.70, first draft, 2026-10-30)
The guild lead: *"where can i give someone a temp key to contribute to shared parses as a raider from another guild"*, and picked the
officer-approved guest link (option A) over a self-serve code.
1. **Flow.** The guest opens Mimic and signs in; Mimic shows a short code; an officer enters it on https://wolfpack.quest/admin/links
   ("Guest links") with a label ("character of guild", required, 64 characters) and an expiry: **1 hour**, **3 hours**, **Tonight (until 1 AM Eastern)** or **7 days**. (Same day, the guild lead: "needs a
   shorter timeframe too, like 1 hour, 3 hours" and "why 6am eastern?": the draft's "Tonight" ran to 6 AM; it now ends at 1 AM,
   half an hour past the raid window.)
   Same code checks as the member link (unknown, expired, already used). Every approval and every revoke is an `audit_log` row.
2. **A guest is not a member.** The session carries `scope = 'guest'`, an `expires_at`, the label, and a synthetic id `guest:<session id>` in
   place of a Discord id (it lands in the `uploaded_by_discord_id` text columns, so a guest's contributions are findable by the prefix). It has no
   roles, is never an officer, and is not in `wolfpack_members`.
3. **What a guest may call**: `POST /api/agent/encounter` (the parse upload), `GET /api/agent/poll` (answered with no streams, only the kill
   switch and version floor, so the guest's agent does not retry a refusal every 1.5 s), and the unauthenticated `GET /api/agent/latest-version`.
   Every other route answers `403 {"error":"guest_scope"}` from `requireAgentAuth`, before the handler runs: one allowlist, not one per handler.
   The agent drops a 4xx upload as permanent and polls on its own cadence, so nothing spins; the refusal is logged once per guest per route.
4. **What a guest upload does**: the parse is recorded and merged into the shared encounter like any raider's. It is treated like a log replay
   for everything live: no Discord parse card, no session totals, no boss auto-kill or timer, no live raid-review count. It writes no /who data,
   no `/parseagents` activity, no raider deaths, and no upload-stats row (those count players, and a guest is not one).
5. **Ends.** Expiry answers 401 like a revoked session (never cached past it); a Revoke reaches the bot within a minute (guest identities are cached
   for 60 s, not 5 minutes).
6. **Open.** (a) The migration `20261030150000_mimic_guest_sessions.sql` must be applied BEFORE the bot deploys. (b) A guest's parse does not get
   a card in the raid thread; say so if the guild lead wants one marked "guest". (c) Whether a guest's character should appear on the website
   (the encounter merge writes `encounter_players` by name; no `characters` row is created by this path).
Where it landed: `draft/guest-link`, not pushed. Bot 4.0.35 (`utils/mimicLink.js`, `index.js`), web 2.1.70 (`/admin/links`).
