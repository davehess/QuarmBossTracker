### 575. [infra-costs] The bot reads the guild's saved raid schedule; what wins when settings disagree (2026-11-13)
The first consumer of `guild_settings` beyond the "Next raid" line (§566, §569: each consumer moves over in its own change,
with a test that the home guild's results are identical). Bot 4.0.79.
- **What reads it:** the raid-window check, the night a timestamp belongs to (night keys, `isRaidNightAt`, the rollover
  hour) and the attendance tick slots. `utils/guildSchedule.js` holds the last good value for 10 minutes.
- **Identical for the home guild:** the seeded row equals the built-in times, and `test/bot-guild-schedule.test.js`
  compares 24 timestamps (window edges, midnight, the 6 AM cutoff, off nights, both clock-change days) against the old
  logic.
- **What wins:** a `DEFAULT_TIMEZONE` or `RAID_NIGHT_ROLLOVER_HOUR` set on the deployment wins over the saved row for
  night keys, because night keys join `raid_nights`, the raid session and the ticks, and an existing deployment must not
  move when its row is first read. With neither set, the saved row applies; with no row, the built-in times.
- **An invalid row falls back whole.** One bad schedule field, or an empty list of days, means the built-in times for
  everything, and one line on stdout per 10 minutes. The website clamps field by field; the bot does not, on purpose: a
  half-right schedule must never drive attendance.
- **Consequence for officers:** an edit on the guild's settings page now moves the real attendance ticks within 10
  minutes. The page says so (web 2.1.135).
- **Not switched, each its own change:** the pre-raid checklist, the midday raid post, the one-hour reminder,
  `/raidnight`, the typical-raid helper and the raid review's reserved tick count still use the built-in times.
- **Known limit:** a raid window that crosses midnight is handled by the window check but gets no attendance ticks after
  midnight.
- **Self-host:** recorded in `docs/DESIGN-selfhost-wizard.md` §3.

### 576. [infra-costs] The site reads only the home guild's fights (pilot build order, step 1) (2026-11-13)
The website reads with the service key, which skips the row-level policies, and its readers of `encounters` carried no
guild filter: a second guild's fights would have appeared on the home guild's pages the day they existed
(`docs/DESIGN-raidmimic-hosted.md` §11). Web 2.1.135.
- **What changed:** 22 service-key reads and writes of `encounters` filter on `guild_id = GUILD_TAG`. Children
  (`encounter_players`, `contributions`) are reached only through a filtered parent, so they were left alone.
- **No visible change:** every fight and raid night in the database belonged to the home guild when this shipped
  (45,756 and 246, checked).
- **One behaviour change:** the parse detail page loads with `maybeSingle()`, so an unknown or foreign id is "not found"
  where it used to show an error panel. A foreign guild's id must not confirm that the fight exists.
- **Left for its own change:** `mergeEncounters` moves contributions, deletes the sources and calls an RPC with no guild
  parameter; filtering one of the three steps would be worse than none, so it needs a guild-checked pre-read of the
  target and sources. `scripts/guild-tables.json` predates `guild_id` on `contributions` and `encounter_players`.
- **The settings page wording** now says what is live: the home guild's raid schedule drives the bot (§575); for a hosted
  guild nothing reads the settings yet.
- **What the draft's own test run missed:** it ran three test files; the full suite found 14 failures in three more
  (fixtures with no guild on their fake fights, one unmocked import) and one in the officer-tools test. All were
  fixtures. They now give fights a guild and include another guild's fights that must stay hidden. The full suite is the
  gate for a draft, whoever wrote it.

### 577. [infra-costs] A hosted guild's upload cannot touch the home guild's rows; the boss list is shared (pilot build order, step 2) (2026-11-13)
Bot 4.0.80. Three writes on the one upload route a hosted guild's session can use (`docs/DESIGN-raidmimic-hosted.md` §11):
- **Threat-snapshot claims** carry the upload's guild when it is not the process guild. The home guild's two requests are
  byte-identical to before (asserted against literal strings), so nothing changes on a raid night.
- **Charm sessions** are stamped with the upload's guild (the scoped client's, else the session's, else the process
  guild's). The write still uses the service key: the table has no guild policy yet, and its unique key includes the
  guild, so a hosted row cannot collide with a home row.
- **The boss list (`bosses_local`) is shared, by decision.** Its keys carry no guild, which matches "standard list of
  bosses" (§566). A hosted guild reads it; a hosted guild's upload no longer adds to it, because the row would be stamped
  as the home guild's.
- **Open, each needs a call before the pilot:** a hosted guild's first fight on an unregistered mob is not saved
  (recommended: let any guild's exact-matched mob join the shared list; the alternative is a per-guild key and per-guild
  rows); and the threat-snapshot upload route stamps the home guild on every row, which only matters once that route
  opens to hosted sessions.
- **One assumption this rests on:** a home session's `hub_guild` is null (`utils/mimicLink.js` sets it only when the
  session's guild differs from the process guild).

### 578. [mimic-overlays] Map: the named mobs you target are remembered per character and zone, on the PC; one filter, three states (the guild lead, 2026-11-13)
*"add in a filter mode on the maps to highlight specific named mobs that you've targetted OR their spawn points, make both
options available. How are we retaining what we've targetted in a zone between mimic upgrades and restarts"*
- **What was true before:** the Map kept no list of targets (the current target and some trails, all lost when the Map
  window reloads). The agent keeps `logsync.targets.json`: the last 50 NPCs targeted on that PC for 24 hours, mixed across
  characters, read by Target Info and never by the Map.
- **The list:** `localStorage` key `wp-map-hunt:<character>`, per zone, 60 mobs a zone and 60 zones. It sits in Mimic's
  data folder with the Map's other settings, which a Mimic update leaves alone (the installer removes that folder only on
  a real uninstall), so it survives closing the Map, restarting Mimic and updating. It does not follow the player to
  another PC and is not part of a shared setup (`wp-map-` is on the private list).
- **Why not Mimic's config file:** it survives exactly the same things and needs a new bridge between the Map and the
  main process. Why not the Map's settings object: Reset and the per-character view snapshot rewrite it wholesale, and
  this is a record, not a setting.
- **What is recorded:** a target that is an NPC and matches a spawn row the server flags as named or a raid target. The
  flag is a heuristic and misses some named mobs, so "+ target" adds any NPC by hand.
- **The filter:** one setting, Off / Highlight their spawn points / Highlight the mobs. A mob's own position is drawn only
  where one was really reported (the current target, or one seen in the last 60 seconds); otherwise its spawn points get
  a dashed ring. A position is never invented.
- **Open:** a copy on the server so the list follows a character between PCs (asked of the guild lead, not built).
- **A review note:** the draft looked up each side-panel row's spawn points by walking the whole zone once per row, once a
  second; it now reads a per-poll map.
