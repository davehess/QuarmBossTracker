### 579. [web] A person's Discord id is read from the sign-in identity, never from the editable profile (2026-11-14)
The guild lead asked for a check of the platform against a list of twenty common web-app holes plus a
percent-encoded-path bypass. The full findings are in the private briefing (a tab of their own); this entry is the rule
that came out of it. Web 2.1.139, bot 4.0.82.
- **The rule:** anything that decides *whose* data a page shows or *whose* guild a form saves reads the Discord id through
  `discordIdOf()` in `web/lib/lockout.ts`, and that function reads only two places: the Discord identity Supabase
  recorded at sign-in (`user.identities`), and `app_metadata.discord_id`, which only server code can set.
  `user_metadata` is never read for an id: the signed-in account's owner can change it from the browser.
- **Why it matters here:** the project allows new accounts, so a session is not proof of guild membership. Membership
  and officer checks were already keyed on the login id; the Discord id was the one value still taken from the profile.
- **Invited password accounts** have no Discord identity. The claim flow now stamps `app_metadata.discord_id` when it
  creates or resets one, and the two existing accounts were stamped from their members row
  (`supabase/migrations/20261114120000_invited_accounts_stamp_discord_id.sql`, applied).
- **Server code that already holds a verified id** (the guild API's answer in the sign-in callback, a members row in
  the claim flow) passes it with `verifiedDiscord(userId, discordId)`.
- **Enforced:** `test/member-lockout-web.test.js` walks every file under `web/app`, `web/lib` and `web/components` and
  fails on an id read out of `user_metadata`, directly or through a `meta` alias. It was run against the old files and
  catches each of the ten it replaced.
- **Bot, same visit:** the three UI-backup routes accept only a plain character name (letters, 2 to 24), and the socials
  index no longer builds a pattern from the uploaded name (`test/ui-layout-list-scope.test.js`). All 146 stored backups
  already have plain names.
- **Checked live and clean:** an encoded or odd-cased path reaches no gated page and no bot route; the middleware-skip
  header does nothing; every view a visitor can read runs with the reader's permissions; no table is without row
  security; the GraphQL extension is not installed; a preview crawler's card is cached apart from the real page.
- **Open, not done here:** the Mimic and agent items (trigger patterns are run unguarded, the standalone agent's local
  page accepts a request with no origin, one link allow-list is loosely anchored) go to `beta` as their own change; the
  bot's Node 20 image is past end of life; unknown bot paths answer 200. `docs/decisions/OPEN.md` carries them.

### 580. [mimic-app] One rule for fitting a window layout to another screen size; key bindings come with the character (2026-11-14)
The guild lead brought a setup from a 2560-wide PC to a 1920-wide one: "Import did not resize correctly onto this 1080
monitor from 1440p" (FB-132), "its off the page", "all of the keybinds are messed up", and, after copying the files by
hand, chat windows "all squished into the middle" that stayed that way "even after resaving in UI studio". Checked
against the real files from both PCs (not committed). Mimic beta `ad460c48`.
- **The rule (`apps/mimic/uiFit.js`), used by both UI Studio's Load + Rescale and the bring-in:** a window keeps its
  place in the free space, not its corner. Flush right stays flush right, centred stays centred, and anything that fits
  the screen ends up wholly on it. Chat windows (MainChat, Chat N) are resized by the screen ratio; for a window whose
  size scales, that rule gives exactly corner times ratio, so the layout keeps its shape. **Every other window keeps its
  size** (#146: shrinking fixed windows drove them into their minimum-size clamp). A tuck of up to 16 px past an edge
  is kept; further out is brought to the edge.
- **Why the old one failed:** it scaled the corner and left the size, so a window docked right landed a quarter of its
  width off a smaller screen. There were two copies of it, and they disagreed.
- **Which block is the layout:** the one the backup was PLAYED at, read from the backup's own eqclient.ini
  `[VideoMode]`. A file keeps a block for every screen size it was ever used at. The real file held equally full blocks
  for 2560x1440 and 2559x1440 (the game ran at 2559) plus an old block for 1920x1080, and "the block with the most keys"
  picked wrong. When the backup was played at another size than this PC, its old block for this size is replaced; when
  it was played at this size, its block is kept and only brought on screen.
- **A chat window's size is one value shared by every screen size**, so fitting twice would shrink it twice. The
  bring-in always starts from the backup's own text. The editor remembers the sizes its last rescale wrote
  (`_fitMemoFor`) and, after a rescale is saved, treats the canvas as the saved layout.
- **Key bindings.** `[KeyMaps]` is replaced as a whole section (a key-by-key merge kept this PC's binding for every key
  the other PC left unbound). Zeal's "per character keybinds" (`zeal.ini [Zeal] PerCharKeybinds`) keeps a character's
  keys in `[KeyMaps_<Char>]`: that section comes with the character (the `zealchar` part, whatever the shared tick
  says), and when this PC has the option on and the backup's PC does not, the backup's `[KeyMaps]` is written as the
  character's own section. On the real files that section went from 2 keys to 43. A backup without the section removes
  nothing here.
- **Whose feature per-character keybinds is: upstream Zeal's, not ours, and not the game's.** Read from Zeal's own
  history (the guild lead asked, 2026-11-14): an upstream contributor added it on 2026-01-01 (upstream pull request
  #125, "Add per character keybind support"), it first shipped in Zeal v1.3.5, and it is off unless ticked in Zeal's
  options. The plain game has one `[KeyMaps]` for everyone. Our fork did not write it and does not change it; our own
  per-character work is the settings FILE (§564), a different thing, which does not move key bindings (see the
  correction there). Mimic only reads the switch and brings the sections.
- **Files copied by hand.** The file then has no place for most windows at this screen size; the game stacks those
  where it likes, and Save wrote only moved windows. Now Save writes every window with no place at this size, a window
  with no place is read from the file's fullest other block (the same one for every window), and a banner offers "Fit
  the WxH layout to this screen". When two blocks are equally full it offers both: nothing in the file says which was
  used last (the order of keys does not: Mimic inserts at the top of a section, the game appends).
- **Also in the change:** windows off the screen get a red edge, a count and a "Bring them on screen" button that moves
  only those; the canvas re-reads after a bring-in (a Save used to write the pre-bring-in places back); a Save no longer
  drops a bring-in queued for camp; Detect reports a display in real pixels (Electron reports Windows' scaled units);
  Zeal's bars are fitted the same way.
- **Not done, on the Decision Desk:** named layouts carry no screen size and are applied unfitted; other resizable
  windows are not resized; an "undo the last bring-in" entry; the Layouts "live" marker.
- **A review note:** I first assumed the key bindings failed because the other PC's own section was left behind. The
  files showed the opposite (the other PC shares one set; this PC keeps them per character), and the first fix would
  not have helped. `scripts/Collect-EqUi.ps1` exists so the next report can be checked against files the same way.

### 581. [mimic-app] Mimic 3.0.10 stable; what the review of the fitted bring-in changed (2026-11-14)

- **The call:** the guild lead, 2026-11-14: "go ahead and push all of this to main." The 3.0.10 beta line is stable
  (main `24660edd`, agent 4.0.85), graduated file by file as in §134. Website previews on beta stayed on beta.
- **A review ran first** and found ten cases; all fixed on beta (`8a705746`) before the cut. The rules that came out:
  - **Which key section is live in a backup is the backup's own switch** (`PerCharKeybinds` in its zeal.ini), not
    which sections are in the file. A PC that shares keys can carry an old `[KeyMaps_<Char>]`; a per-character PC
    still has a `[KeyMaps]` nobody reads. A backup with no zeal.ini falls back to the section being present.
  - **The switch itself is never copied** with the shared Zeal part: it says where THIS PC's game reads keys.
  - **A backup made on this computer is put back as it was** (a version Mimic kept here, or a cloud backup carrying
    this PC's name): its block for this screen size is kept. "How it looks on the other PC" has no meaning there.
  - **"Made for another screen" needs many windows without a place** (a fifth, at least three). A member who changed
    screen size and has played since has a layout in use; the button would lay the old screen's layout over it.
  - **A save that waits for the camp leaves guessed places to the game.** The game writes every window's place at
    camp, so a place the canvas only guessed (the file had none, the window was not moved) would land over where the
    window really was. Exception: a layout made for another screen, where the fitted places are what is being saved.
  - **The queue message says what the queue does:** "close" for the half that writes eqclient.ini / zeal.ini.
- **Considered and not done:** an "only if absent" flag on those guessed writes all the way into the ini writer. It
  would have broken the case the fit was built for (files copied by hand, saved while in game: the game's camp write
  gives every window a place, so "only if absent" writes nothing and the layout stays scrambled).
- **Known ceiling:** a direct save with the editor left open across a camp can write a guessed place over the
  game's. Closing it needs the editor to notice the file changed under it; not built.
- **Ships report-only:** the agent-update signature check (`SIG_MODE 'warn'`) and the IPC sender check
  (`IPC_GUARD_MODE 'report'`). Flipping either is its own release and its own call.

  member's data (`test/lab-drafts.test.js`: nothing under the lab reads the database, the session or a secret). The

  show the hard states on demand (a cursed raider, eleven blocked raiders, a wipe).

### 583. [mimic-app] A release gets a second review that is told to refute; what it found in 3.0.10 and the drafts (2026-11-14)

- **What happened:** after the 3.0.10 stable cut and the six site drafts, a second review ran with nothing but the
  code and the intent: four reviewers by area, then for every medium or high finding a second reviewer told to
  REFUTE it, by reproducing it or showing it cannot happen. Plus a measured visual check of every lab version.
- **The rule that came out:** a fix written to a reviewer's finding is reviewed again before it is called done. The
  first round's fixes for 3.0.10 (§581) were themselves the source of two of the three faults found here: dropping
  the per-character switch from the copy was right but left the reverse direction with the wrong keys, and "same
  computer" was built as "read everything at this screen size", which lost the size the backup was played at.
- **The rule for drafts:** a draft's fixture is made to look like the real data, measured first. Four of the seven
  draft faults were invisible with the made-up data: the real spawn board has 252 of 261 bosses with no timer
  running (the fixture had 3 of 40), contribution detail is deleted after 7 days, defender lists include the boss,
  and some PoP preflags do not gate entry. A fixture now carries the real proportions; a draft that states a game
  rule ("cannot enter") needs the rule from the scripts or the database, not from the draft's own guess.
- **Held on purpose:** the bot's backup download returns no `machine_name`, so a cloud backup from the same PC is
  never recognised as its own. Turning it on before 3.0.11 is stable would put 3.0.10 installs on the path the
  second fault broke. It ships with the stable cut (Decision Desk card "Mimic 3.0.11").
- **Where:** Mimic beta `6939cdf1`; site drafts beta `7de1115e`; STATUS 2026-11-14 (morning).
