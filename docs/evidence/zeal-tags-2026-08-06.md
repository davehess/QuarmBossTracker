# Zeal `/tag` spawn-id capture — raid night 2026-08-06

Snapshot pulled live at 23:1x ET from `character_live_state.zeal_tags`, which is
overwritten every few seconds and has **no durable table**. Kept here because it
is the first field evidence that the `/tag` chat channel delivers the one datum
the Zeal named pipe does not: a **spawn id**.

## Why this matters

`CLAUDE.md` (Scope boundaries) states, correctly for the *pipe*:

> ≥2 identically-named mobs alive at once can't be told apart from the pipe …
> Do NOT design features that need N≥3 simultaneous same-name identities — the
> data can't support it.

The pipe still can't. **The tag channel can, for tagged mobs.** Tonight caught
three simultaneous `protector of Zek` resolved to distinct ids (148 / 149 / 150),
plus two `an aged caretaker` (57 / 61) and two `an ancient sentry` (39 / 45).
That is exactly the N≥3 case, disambiguated.

The constraint is now **coverage, not capability**: a mob is only identifiable if
somebody tagged it. Three raiders tagged all night — Dafeet, Canniball, Jankzer.

## Gap this exposes

`zeal_tags` is a jsonb column on the live-state row, replaced on every upload.
Nothing writes tag history anywhere. Tonight's Rallos Zek tags were already gone
from the live rows by 23:13 — this file is the only copy. If tag-derived
identity is going to be load-bearing (same-name split, threat attribution), it
needs a durable table keyed `(zone, spawn_id, first_seen)`.

## Is the spawn id actually tied to the mob? (asked 2026-08-06, answered: NOT PROVEN)

**No mob was tagged by two different people tonight.** Every spawn id maps to
exactly one tagger — Jankzer 39/145, Canniball 57/61/71/149, Dafeet the rest. So
the direct confirmation does not exist in this data.

**And the current code cannot capture it.** `_zealTags` is a `Map` keyed by
spawn id, so a second tagger on the same mob overwrites the first before the
snapshot ever uploads. The confirming observation is destroyed at parse time.
Any attempt to prove this in-band needs the map keyed `(spawn_id, tagger)` first,
or a raw tag log.

**Strongest available evidence — the three protectors, and it is circumstantial:**

| tagger | spawn_id | when |
|---|---|---|
| Dafeet | 150 | 21:32:42 |
| Dafeet | 148 | 21:33:22 |
| Canniball | 149 | 21:56:26 |

Kael has exactly three `protector of Zek` spawn points (338001/338002/338003, all
`pathgrid=0`, 33-36 units apart on one wall). Two independent clients produced
three distinct contiguous ids matching that count, with Canniball's landing
exactly in Dafeet's gap. Suggestive that the numbering is server-assigned and
shared — but n=1, and the observations are 23 minutes apart against a **24.4
minute respawn**, so a respawn may have intervened. Do not cite this as proof.

`Derakor the Vindicator` held id 114 from 21:35:52 to 21:36:56 across four
receiving agents — stable over ~64s, but all from one tagger's client.

**Correction (Hitya, from the PQDI npc page):** an earlier note in this file
glossed Derakor's `respawntime` of 1,700,000s as "the ~19.7-day boss timer". It
is not a timer at all — his real instance timer is **2d18h (66h)**, which is what
`data/bosses.json` carries. See the cheatsheet warning; 472.22h is a sentinel.

**The cheap decisive test:** two people tag the same mob within the 120s
freshness window and compare the numbers on their own screens. Matching ids ⇒
server-assigned. No deploy needed; the in-band version does need the map fix.

## Not a spawn point, and no pathing

`eqemu_spawn2.id` in Kael runs 337,820-368,376; tags carry 39-318. Disjoint —
the tag's number is a runtime **entity id**, not a spawn point, spawn group, or
NPC type. There is no join to the catalog.

Pathing is unavailable for two independent reasons:
- Everything tagged tonight is **stationary** (`pathgrid = 0`) except Derakor.
  Only 26 of Kael's 242 spawn points have a grid at all.
- We do not mirror `grid` / `grid_entries`, so even Derakor's `pathgrid = 23` is
  a dangling pointer — we know it roams and nothing more. Adding those two
  tables to `sync-quarm.yml` would close that gap cheaply.

## Unrelated bug found while chasing this

`character_live_state` holds **418 rows whose `character` is `<Player>'s
corpseNNNN`** — oldest 2026-06-04, still being written 2026-08-06 23:16. Corpses
are getting live-state rows as though they were characters, inflating anything
that counts characters off that table. Two notes: the `NNNN` suffix is itself an
entity id (a second, unused spawn-id source), and `corpse65436` recurs across
nine different players, so that value looks like a sentinel rather than a real id.
