Source: their `FEATURES.md` at `jasonsoprovich/pq-companion`, read 2026-08-13.

## 1. The serialization answer

**Everything ships inside the installer. There are no remote data sources at
all** — not an API, not a scrape, not a CDN.

```
EQEmu MySQL dump (sql/)
   └─ backend/cmd/dbconvert  (Go CLI, --from-dump | --from-mysql)
        └─ backend/data/quarm.db          ← SQLite
             └─ electron-builder.yml  extraResources
                  └─ shipped in the app bundle
```

- Built by a GitHub Actions **`data-release`** workflow, on manual dispatch or a
  push under `sql/**`; the artifact is uploaded to a **`data-latest` prerelease**
  and the app reads that to detect new data versions.
- **Validated before it ships: 14 row-count checks + 10 FK integrity checks +
  spot checks, and a row-count mismatch FAILS THE BUILD.** That is the part
  worth stealing outright — see §6.
- Zone geometry is a *second* SQLite file, `maps.db`, generated by `cmd/mapgen`,
  a Go port of the `.s3d`/WLD client-file reader.
- Per-user state is a third SQLite (`~/.pq-companion/user.db`, WAL) plus
  `~/.pq-companion/config.yaml`.

**Ours is the mirror image**, and neither is wrong:

| | pq-companion | us |
|---|---|---|
| Converter | Go `dbconvert` | Node `scripts/sync-from-eqmac.js` |
| Store | SQLite file in the bundle | Postgres (Supabase) |
| Reach | offline, zero latency | needs network |
| Freshness | **frozen at build**; new data = new release | weekly sync, live for everyone at once |
| Distribution | every user downloads the whole DB | one copy, queried |
| Multi-user | impossible by construction | the entire point |

The honest trade: they win the plane flight and the raid-night outage; we win
freshness, size, and the fact that one person's correction fixes it for the
guild. Worth recording in `DESIGN-selfhost-wizard.md` because a self-hosting
guild with a flaky box might genuinely prefer their shape.

## 2. Zone + spawn info — we had the tables, not the columns

Every zone feature they list is driven from tables **we already mirror**:

| Their zone surface | Source | Do we have it? |
|---|---|---|
| Zone list + attributes | `zone` | table yes — **columns no**, see below |
| NPC level range per zone | correlated subquery over spawn chain | tables yes, surface no |
| Zone connections | `zone_points` → target zone | `eqemu_zone_points` (1,360) |
| Spawns (group + solo) | `spawn2 → spawnentry → npc_types` | `eqemu_spawn2` (43,654) |
| Respawn timers | `spawn2.respawntime` | ✅ we carry `respawntime` + `variance` |
| Ground spawns | `ground_spawns` | `eqemu_ground_spawns` (514) |
| Forage | `forage` | `eqemu_forage` (1,243) |
| Zone drops (capped 500) | loot tree over zone NPCs | full loot tree mirrored |

**The one real gap was columns, not data.** Our `eqemu_zone` carried
`short_name, long_name, zone_id, expansion, file, safe_*, min_status, note` and
nothing else, so we could not answer "can I bind here / can I levitate / is this
a hot zone / what is the XP multiplier" even though the upstream table has all
four. Fixed in `20260813030000` (`cast_outdoor`, `hotzone`, `can_levitate`,
`can_bind`, `zone_exp_multiplier`); the sync transform needs the matching pick
list before they populate.

**Where we are ahead on zone data:**
- `eqemu_npc_emotes` (4,144 rows) — DB-driven mob chatter. Not in their feature
  list at all.
- **Mob scripts** (`eqemu_quest_scripts`, 2026-08-13) — the `.lua` behaviour
  files. Nothing in a SQL dump can produce these, and they are the only source
  for script-driven emotes and boss timers. They have no equivalent.
- `eqemu_fishing`, `eqemu_object`, `eqemu_doors`, the AA tables.

**What they surface that we still don't:** the *pages*. They compute NPC level
bands per zone and a zone-wide drop list; we hold the same rows and have never
put them on a screen. That is a web task, not a data task.

## 3. Tradeskills — the data is already here

`eqemu_tradeskill_recipe` (7,448) and `eqemu_tradeskill_recipe_entries` (54,229)
have been mirrored all along. Their three features on top:

1. **Tradeskill Leveling planner** — staged plan from current skill to a target,
   picking recipes by skill-up band and total cost, with **recursive
   sub-combine costing** (intermediate items you must craft first) and a warning
   when a step crosses into another tradeskill.
2. **Combine success calculator** — per-recipe success/failure % from skill and
   crafting-stat gear, **ported from the EQMacEmu server formulas**, including
   the trivial breakpoint where combines stop failing, plus skill-up chance.
   Accounts for Jewelcraft/Alchemy/Poison Mastery AAs and Maelin Starpyre.
3. **Cultural recipe awareness** — flags race-locked recipes so a plan never
   routes you into a combine your race cannot perform.

⚠ **The most useful thing in this section is their retreat.** As of v0.17.4 they
*replaced* the DB-derived "fastest/cheapest" solver with **hand-curated
recommended paths**, because a solver reading only the database "skewed toward
recipes the database alone could see and missed farmed materials tried-and-true
guides account for."

That is a direct warning for us: `CLAUDE.md` parks a "tradeskill advisor on
`/me`" and the obvious build is exactly the DP solver they abandoned. Their
formulas (from server source) are worth reimplementing; their *optimizer* is
documented as having been wrong. Curated paths + a calculator beats a solver.

## 4. Piper / Kokoro — local neural TTS

**Their design (v0.16.1):** Piper is a **user-installed external tool, nothing
bundled** — the same posture we already take with Zeal and EQW. The app detects
the executable and voice model, spawns it to synthesise, and:

- an optional **warm-process mode** so the first callout of a fight is not late;
- **caches generated audio by content hash**;
- **falls back to the browser voice if anything fails.**

**Why this matters for us specifically.** Our trigger TTS is browser
`speechSynthesis` inside overlays, and it has already cost us a bug — the
user-activation fix (#120). A local neural voice removes that whole class of
problem *and* is markedly clearer than a robotic system voice through a headset
mid-raid, which is the only moment our TTS matters.

The caching detail is the clever part and it fits us better than it fits them:
raid callouts are a small, highly repetitive set of strings ("CH ON TANK",
"START CURSE CURES"), so a content-hash cache means each phrase is synthesised
once ever and thereafter plays instantly from disk. That is *lower* latency than
`speechSynthesis`, not higher.

**Kokoro** (Hitya's addition) is the newer local neural TTS — better prosody
than Piper, heavier to run. Same integration shape, so the sane build is a
**voice-backend interface** with `browser | piper | kokoro` behind it rather
than wiring either one directly. Fall back to browser on any failure, always.

Not built. Ranked: worth doing, after the things already in flight.

## 5. Windows code signing — their approach beats our closed ticket

**Theirs (Task 6.3):** `electron-builder.yml` gains
`signingHashAlgorithms: ['sha256']`; the release workflow forwards
`WIN_CSC_LINK` + `WIN_CSC_KEY_PASSWORD` to the packaging step. **When both
secrets exist the installer and its NSIS stub are SHA-256 signed; when they are
absent the build succeeds unsigned and CI does not fail.** They also evaluated
and *rejected* migrating to Electron Forge, on the grounds that electron-builder
already does Windows signing natively through env vars — no toolchain change.

**Ours:** `docs/code-signing.md` is marked CLOSED (SignPath Foundation declined
— user base too small), and the signing block was **removed** from
`release-mimic.yml` (see the comment at line 167).

⚠ **Two things to fix, both cheap:**

1. **`docs/code-signing.md` is stale.** It still reads *"pre-staged, OFF… the
   signing pipeline is wired into `release-mimic.yml` but inert."* It is not
   wired — it was deleted. A doc claiming a pipeline exists when it does not is
   exactly the failure mode that made `/recall` wrong about #202.
2. **Re-wire the generic path, not the SignPath one.** Their shape is
   provider-agnostic: two secrets, graceful unsigned fallback, zero CI risk. It
   costs nothing to carry while unsigned, and turns "we got a certificate" from
   a workflow rewrite into adding two repository secrets. The realistic provider
   is **Certum Open Source (~$80/yr)**, already named as our fallback.

## 6. Other things worth knowing (from the same read)

- **Their build gate is better than ours.** 14 row-count + 10 FK checks that
  *fail the build* on drift. Our sync writes `data/sync_state.json` and commits
  it, but nothing fails when a table silently arrives empty — and we have
  already been bitten twice by exactly that class of silence (the 6 tables no
  migration created; `npc_spells` parsed but never listed in `ORDER` so it never
  reached Supabase). **Highest-value steal in this document.**
- **Spell Emote Customizer (v0.18.0)** — they let users edit `spells_en.txt`,
  store the overrides *structurally* so a server patch republishing the file
  does not wipe them, and — the interesting bit — **surface any trigger whose
  regex was written against the old text and propose a diff.** That is our new
  `trigger_text_audit` view approached from the opposite direction: they catch
  drift at edit time, we catch it by corpus search. The two compose.
- **Live Maps (v0.19.0)** — `.s3d`/WLD reader ported to Go, spawn points drawn
  with patrol routes and trap markers, live position off the Zeal pipe, and
  annotations that write back to the in-game `/map`. This is report 03's parked
  item, now clearly further along on their side.
- **Zone Loot Lockouts** — per-zone view of every character's lockout status.
- **Discord Voice overlay (#150)** — worth noting they *wanted* local Discord
  RPC and **Discord declined**; they fell back to embedding Discord's hosted
  StreamKit overlay page. Saves us discovering that ourselves.
